# Magento Modernization Backend

Fresh Magento Open Source backend workspace for the infrastructure
modernization project.

This repo is the clean project baseline. The sibling `vusa244/` tree is legacy
reference material only and must not be copied into this project.

## Target Baseline

- Magento Open Source `2.4.8-p4`.
- PHP `8.3` for local development.
- MySQL `8.4` for local Cloud SQL parity.
- Redis `7.2` for cache, full page cache, sessions, and locks.
- OpenSearch `3` for catalog search.
- nginx `1.28` in front of PHP-FPM.

The runtime architecture rules live in
`docs/architecture/runtime-contract.md`.

## Local Setup

Prerequisites:

- Docker with Compose v2.
- Current Magento Marketplace credentials.
- No raw production database dump in this repo tree.

Create local files:

```bash
cp .env.example .env
```

Composer credentials are loaded from `../composer-auth.json` by default. You can
also set `MAGENTO_COMPOSER_AUTH_FILE=/path/to/auth.json` or create a local
ignored `auth.json`. Do not commit credential files.

Start the local stack and install Magento:

```bash
scripts/dev/setup-local.sh
```

The setup script runs `composer install`, starts Docker services, and installs
Magento into the local containers. When it completes:

- Storefront: `http://localhost:8080/`
- Admin: `http://localhost:8080/admin`
- Mailhog UI: `http://localhost:8025/`
- OpenSearch: `http://localhost:9200/`

## Common Commands

```bash
scripts/dev/composer validate --strict
scripts/dev/magento cache:status
scripts/dev/cache clean
scripts/dev/test
docker compose up -d
docker compose down
```

## Data Loading

Normal local startup uses a clean Magento install. It must not depend on the raw
production database dump in the workspace root, and raw production dumps must
not be copied into this repo.

Use sanitized or rehearsal data only. A rehearsal dataset is acceptable when it
has already had customer data, secrets, payment data, session data, admin
accounts, private tokens, raw exports, and production-only integration values
removed or replaced.

Place sanitized import artifacts under `var/import/sanitized/` after the Magento
project has been installed. That directory is intentionally ignored as a runtime
artifact and should not be added to Git or the Docker build context.

When a task needs data beyond the clean install, document the dataset in that
ticket or runbook:

- dataset name and source environment
- sanitization process or owner
- import command or script
- expected local verification steps
- cleanup/reset steps

If no sanitized dataset is available, keep working from the clean install and
track data-dependent validation as a separate follow-up.

The completed local migration rehearsal contract for ECOM-7 lives in:

- `docs/ecom-7/migration-rehearsal.md`
- `docs/ecom-7/core-first-import-plan.md`
- `docs/ecom-7/final-validation.md`

Important ECOM-7 follow-up boundaries:

- `ECOM-77` owns retained extension-backed data after module decisions are
  finalized.
- `ECOM-78` owns source media export and migrated GCS media-path validation.

## `app/etc/config.php`

For the initial clean baseline, `app/etc/config.php` is generated by local
setup and stays uncommitted. Once `ECOM-20` finalizes the module keep matrix,
the project should either commit an environment-neutral `config.php` or add a
repeatable generation step that enables only approved modules.

## Secret Rules

- Keep real Composer credentials in local `auth.json` or CI secrets only.
- Never copy credential-bearing Composer repository URLs from `vusa244`.
- Keep `.env`, `auth.json`, `app/etc/env.php`, database dumps, raw exports,
  generated files, `vendor/`, and raw media out of Git and Docker contexts.
- Run `scripts/security/scan-secrets.sh` before sharing changes.
